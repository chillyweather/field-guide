# Field Guide

A Figma plugin that identifies user-interface components from regions a designer marks,
and says plainly when it cannot tell.

You mark regions on a screenshot. The plugin names them — `Button`, `Checkbox`, `Modal Dialog` —
and flags the ones it could not settle. The dropdown you would have used forty times
becomes the thing you use five times.

## How it works

Three steps, deliberately separated.

1. **The design file supplies what pixels cannot.** Size, proportion and position on
   screen go along with the crop. A full-width band at the top of a frame is a header
   and not a card, and no crop of it says so.
2. **A vision model describes, and does not decide.** It is asked for shape, fill,
   text, icons and visible state, and explicitly forbidden from using design-system
   vocabulary. The identification is not its job.
3. **[Jev](https://docs.typesafe.ai) identifies.** The guide in
   `taxonomy/components.json` becomes the `criteria` of a Choice question — each entry
   already has a `what`, a `not_for` and `examples`, which is the shape Jev asks for and
   also the shape a field guide entry has always had. A second Choice on behaviour and
   five Noul probes ride along in the same call, and the composition logic in
   `weigh()` decides what to do with the answers.

## What confidence is for

The gates follow TypeSafe's published bands: act alone above `0.9`, ask a human below
`0.5`. Two extra rules do the interesting work.

- If the behaviour answer disagrees with the family recorded for the chosen component,
  the answer is not trusted however high its probability.
- **If the top two options sit within `0.15` of each other, that is not a weak answer.
  It is a taxonomy that does not separate them.** The plugin reports it as a confusion
  pair and names both.

That last case is the reason the guide contains `Chip` and `Badge`, `Button` and `Link`,
`Checkbox` and `Toggle`, `Card` and `Modal Dialog`. Design systems argue about these,
and the probability distribution measures the argument.

## The guide

`taxonomy/components.json` — thirteen entries drawn from Material 3, IBM Carbon,
Shopify Polaris and shadcn/ui, so that any reader can check them. Where those systems
genuinely disagree, the entry records the disagreement in `contested` rather than
resolving it.

Editing the guide is the main way to change this plugin's behaviour. No prompt to tune.

## Working offline

The API is in early access and was unstable on 20–21 September 2026. Nothing here
needs it to be up.

```
node test.js                              # the decision logic, against fixtures
node build.js && tick "work offline"      # the whole plugin, from fixtures
node probe.js                              # five Jev calls, ~$0.0005
```

`fixtures/offline.json` holds five specimens chosen to exercise every branch of
`weigh()`: two clean identifications, a confusion pair, one genuinely uncertain,
and one where a high probability is held back because the behaviour answer
contradicts it. They are generated by `fixtures/make-fixtures.js` rather than typed,
so the probabilities always sum to 1 and the confidences are derived the way the
documentation derives them — a fixture that could not have come off the wire
teaches the UI to handle a response the API will never send.

`probe.js` is the one that closes the gap. It makes a real call, saves the raw
response to `fixtures/jev-live.json`, then checks it field by field against what
`src-weigh.js` and the UI actually read, and names anything that differs. Run it
before trusting any of this against the live API.

## Keys

Copy `.env.local.example` to `.env.local` and fill it in. That file is gitignored,
and nothing in this repo prints it. `probe.js` reads it directly rather than taking
the key from a command line, so it stays out of shell history and out of the
transcript of anyone driving a session here.

The plugin itself does not use it: keys are entered in the panel and kept in
`figma.clientStorage`.

## The Jev CORS shim

A Figma plugin's UI runs in a sandboxed iframe whose origin is the literal string
`null`. TypeSafe runs an origin allowlist and its preflight answers *"Disallowed CORS
origin"* with a 400, and `Origin` is a forbidden header, so page JavaScript can neither
set nor remove the one thing being judged. There is nothing to fix on the plugin side.

So Jev is reached through `proxy.js`, a dependency-free shim on `localhost:8787`:

```
node proxy.js     # leave running while the plugin is open
```

Figma rejects a bare IP in `allowedDomains`, so the plugin calls the name `localhost` and
the shim binds both loopback addresses — on macOS that name resolves to `::1` as readily
as to `127.0.0.1`, and listening on only one fails intermittently in a way that looks
like a CORS problem all over again. The entry lives in `devAllowedDomains`, so it is a
development affordance and never ships in a published build.

It takes the key from the panel if the panel sends one, and otherwise from
`.env.local` — so the key can stay in one gitignored file rather than also living in
`figma.clientStorage`.

OpenAI needs none of this: it answers `access-control-allow-origin: null` and is
called directly. Only Jev is affected. The day `api.typesafe.ai` allows the null
origin, put it in the panel's Jev base URL field and delete the proxy — nothing else
changes.

## Running it

```
node build.js     # stitches the guide into dist/ui.html — no dependencies
```

Then in the Figma desktop app: **Plugins → Development → Import plugin from manifest**,
and choose `manifest.json`.

Two API keys are entered in the plugin and kept in `figma.clientStorage`: one for
TypeSafe, one for the vision model. Neither is committed or bundled.

Network calls happen in the UI iframe, which is the only half of a Figma plugin that has
network at all; `code.js` only exports regions and renames nodes.

## The vision half

Any OpenAI-compatible host. The seam is `describeRegion()` in `src-ui.html`, and the
provider is three fields in the panel — key, base URL, model — not a code change.

The vision model describes and must not decide. Measured on one image, 22 September
2026, three identical calls each:

| model | leaked vocabulary | latency | input tokens |
|---|---|---|---|
| gpt-4o | 0/3 | 2125 ms | 402 |
| gpt-5.2 | 0/3 | 4418 ms | 164 |
| gpt-4o-mini | **1/3** | 2456 ms | **8647** |
| gpt-5-mini | — | — | unusable: reasoning consumed the cap, empty content |

`gpt-4o` is the default. Two things in that table are worth keeping: the cheap model
was the expensive one — gpt-4o-mini bills images at roughly twenty times the tokens —
and it was also the one that leaked.

Because 0/3 is not a guarantee, `src-vocabulary.js` masks design-system nouns out of
every description before the guide sees it, in production and not only in the probe.
A description reading "a toggled position" carries the answer, and Jev would then be
reading a verdict rather than reaching one.

## Known limits

- One vision call per region. The better shape is a single call over the whole screenshot
  with numbered outlines. Not done here.
- Overlay is hard to judge from a crop, which is why the context image is sent — and it
  is still the weakest distinction in the guide (`Card` against `Modal Dialog`).
- Probabilities are the model's, not a calibrated estimate of correctness. Treat the
  confusion-pair signal as a prompt to go and look, not as a verdict.
